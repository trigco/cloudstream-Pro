# Phase 8.94 — Feed categories/chips regression fix + flat bottom nav

On top of 8.93b (head 5b922f12). Three jobs: (1) the Feed's
category rows and tag chips vanished in the 8.92 build —
diagnosed from code, fixed; (2) the floating pill bottom nav
replaced with a flat full-width bar (his order: the pill
"sucks", community comments call it the worst nav);
(3) Feed search moved to a pushed standalone Search page
(his 2026-10-30 09:11 decision, added after Jobs 1–2 were
already pushed as 267890b5 — Job 3 ships as this phase's
follow-up commit).

## Job 1 — Root cause: the 8.92 chrome scheduler starved itself

Device evidence (8.92b build): Feed header + ONE chip ("All")
+ "For You" + the full poster grid. No category rows, no tag
chips. In 8.91b the same surfaces worked (main-thread compute
could not be interrupted). The pool itself loads fine — the
grid is full — so the break is entirely inside the rows/chips
delivery path. Traced state flow, all in
`ui/feed/FeedFragment.kt` (pre-8.94 line numbers):

1. The observer (line 325/341) reassigns `pool` to a fresh
   filtered list on every `Resource.Success` and calls
   `scheduleChromeUpdate()`.
2. Pre-8.94 `scheduleChromeUpdate` (lines 975–1015)
   UNCONDITIONALLY ran `chromeJob?.cancel()` (line 988) and
   launched a replacement pass on `Dispatchers.Default`.
   `computeChrome` contains no suspension points, so a
   cancelled pass still burns the full compute and only
   discovers the cancellation at `withContext(Dispatchers.Main)`
   (line 992) — where it dies WITHOUT posting anything.
3. The triggers that kept cancelling are generated by the
   Feed itself: the observer pre-kicks
   `MetadataResolver.resolveMeta` for the pool's first 24
   entries (lines 337–339), `FeedAdapter.bind` kicks
   `resolveMeta`/`resolve` for every uncached card, and every
   NEW store fires the listeners — `MetadataResolver.
   storeMeta` (MetadataResolver.kt ~line 158) and the rating
   store in `resolve` (~line 239). Both fragment listeners
   re-arm `metaApplyRunnable` (900 ms debounce), whose `run()`
   calls `scheduleChromeUpdate()` (line 219) whenever the
   grid is idle.
4. A pass is multi-second work on the Android 8.1 phone:
   ~40–70 tag evaluations over the whole pool
   (computeChromePass rows + computePresentTags), and the hot
   per-entry calls — `MetadataResolver.metaCachedFor` (a
   SharedPreferences `getString` on every miss, misses not
   negatively cached there, plus `cleanPosterTitle` and two
   `Regex` instantiations per `normalize()` call) and
   `TitleResolver.cachedType` — are paid again for every
   (tag × entry) pair.
5. So during and after load, landings recur faster than a
   pass completes; each debounced landing cancels the
   in-flight pass and restarts from zero. NO pass ever
   reached the adapter: `categoryRowsAdapter` stayed empty
   and the chips stayed at the initial
   `buildCategoryTabs(binding, listOf("All"))` from
   `onBindingCreated` (line 279) — exactly the screenshot.
   (Proof it is the delivery, not the content:
   `computePresentTags` adds `TAG_TRENDING` unconditionally
   for a non-empty pool, so any single completed pass would
   at minimum have produced a Trending chip and row.)
6. Compounding it, the old Main continuation discarded a
   finished result when `pool !== poolSnap` (page 1 → page 2
   progressive publish) with NO re-schedule — the result was
   dropped on the floor and recovery depended on some later
   trigger surviving the cancellation chain in (5).

### The fix (FeedFragment.kt only)

- **Coalescing scheduler, no mid-flight cancellation.**
  `scheduleChromeUpdate` now: if a pass is running, it only
  sets `chromeDirty` and returns. `launchChromePass()` runs
  one pass; its Main-thread completion (a) posts rows +
  chips when the snapshot is still the current pool and the
  Feed is still browsing, then runs ONE follow-up pass if
  `chromeDirty` was set; (b) if the pool changed mid-pass or
  a search/filter took over, it routes back through
  `scheduleChromeUpdate()` — fresh pass over the new pool,
  or the hidden-rows branch when a search/filter is live —
  instead of silently discarding. The job is now cancelled
  only by the search/filter/empty branch (rows are being
  hidden anyway) and in `onDestroyView`. Net guarantee: the
  very first pool post's pass always reaches the adapter,
  and every later input change is eventually reflected by
  exactly one follow-up pass.
- **Pass-local meta memo** (`passMetaCache`, installed by
  `computeChrome` around the renamed `computeChromePass`
  body): `metaOf` answers repeat (tag × entry) checks from
  a ConcurrentHashMap instead of re-reading
  SharedPreferences + re-normalising the title every time.
  This cuts a pass from ~40–70 × pool resolver lookups to
  one lookup per pool entry. Main-thread callers are
  unaffected (the memo is null outside a pass).
- **`sectionTagsOf` cache lock**: the background pass and
  the main thread (grid filter) both call it; its plain
  HashMap cache is now guarded by `sectionTagsCacheLock`
  (brief holds; the monitor is re-entrant for the nested
  calls inside one pass).

Unchanged: the 8.91/8.92 row vocabulary and slot order,
thresholds (≥3 items / ≤20 rows / 20 per row), per-provider
rows, the ≥80% region dedupe, Feed Categories settings
respect, the FeedViewModel (progressive publish, Default
dispatcher), and the in-feed search — verified against the
new scheduler: typing still hides the rows synchronously
(`applySearch` → `hideCategoryRows`), clearing the query
calls `scheduleChromeUpdate` and the rows re-post from the
next completed pass; pull-to-refresh posts a new pool,
which the observer routes into a pass (or the dirty
follow-up), so rows re-post after refresh too.
(Superseded in part by Job 3 below: the in-feed text input
was removed the same morning by his final decision — the
filter path through `applySearch` and the scheduler
interplay verified here are unchanged; only the text entry
point moved to the pushed Search page.)

## Job 2 — Flat bottom bar (presentation only)

The nav is a Material `BottomNavigationView`
(`@+id/nav_view` in `activity_main.xml`, menu
`bottom_nav_menu`: Home, Search, Feed, Library, Downloads,
Settings). No navigation logic, ids, order or behaviour
changed — including MainActivity's scrub/long-press
handling, the icon-pop animation, destination-driven
visibility, and Home's scroll auto-hide (it translates
`nav_view` by `height + bottomMargin`, which still works
with a 0 margin).

- `activity_main.xml`: margins (20dp sides / 18dp bottom)
  removed — the bar spans the full width, flush to the
  bottom; elevation 12dp → 0dp; `labelVisibilityMode`
  unlabeled → **labeled** (every destination now shows
  icon + label — the old bar showed icons only);
  background → new `@drawable/bg_nav_bar`.
- `res/drawable/bg_nav_bar.xml` (new): solid #0B0B0B with
  a 1dp top hairline at white ~9% (#17FFFFFF). No corners,
  no stroke box. (`bg_nav_floating` is now unreferenced
  and left in place; the TV layout never used it.)
- Active state: icon + label stay white / grey via the
  existing `@color/item_select_color`; the ONE red accent
  is a small red indicator pill behind the active icon —
  new `NavActiveIndicator` style in `styles.xml`
  (`Widget.Material3.BottomNavigationView.ActiveIndicator`
  parent, `android:color` = `@color/colorPrimaryRed`),
  applied via `app:itemActiveIndicatorStyle`.
- Bar height is unchanged (`@dimen/nav_view_height` =
  70dp, shared with the TV layout, which is untouched);
  only the pill's 18dp bottom margin disappeared, so the
  nav zone shrank 88dp → 70dp. Every compensation that was
  computed from the 88dp zone drops by exactly 18dp,
  preserving each screen's existing air gap:
  - `fragment_feed.xml`: grid paddingBottom 88 → 70dp
  - `fragment_home.xml`: list paddingBottom 100 → 82dp;
    Random FAB marginBottom 112 → 94dp
  - `fragment_search.xml`: three result lists 100 → 82dp
  - `main_settings.xml`: 100 → 82dp
  - `fragment_library.xml`: tab strip marginBottom
    100 → 82dp; ViewPager paddingBottom 140 → 122dp;
    FAB wrapper marginBottom 140 → 122dp; loading grid
    paddingBottom 120 → 102dp
  - `fragment_downloads.xml`: list paddingBottom
    200 → 182dp; queue bar marginBottom 100 → 82dp
  - `fragment_child_downloads.xml`,
    `fragment_download_queue.xml`: 100 → 82dp
  - `feed_mini_player.xml`: mini player marginBottom
    100 → 82dp (it floats above the bar on the Feed)
  Deeper settings sub-pages keep their 100dp paddings —
  still ≥ the 70dp zone, so nothing can hide behind the
  bar there; they simply keep 18dp of extra air.

## Deviations

- The red accent is the active item's indicator pill, not
  a top bar segment: BottomNavigationView has no per-item
  top-bar primitive, and the indicator pill is its native
  active marker (white icon on red reads clearly and keeps
  red sparing — one small pill, nothing else in the bar is
  red).
- Labelled mode with SIX items on narrow phones is dense
  but renders (labels are the menu titles he already sees
  in the rail); dropping a destination to make room was
  explicitly out of scope.
- No diagnostic build was shipped for Job 1: the failure
  mechanism is fully determined by the code paths above,
  and the fix removes the mechanism (cancellation +
  silent discard) rather than tuning around it. Per the
  build loop, green CI = ready for his device check, not
  proof; the checks that confirm this build: Feed shows
  tag chips beyond "All" and the category rows after load,
  rows survive scrolling and a pull-to-refresh, the Feed
  header's search button opens the pushed Search page
  (Job 3) and Back returns to the Feed with scroll and
  rows intact, and the bottom bar is flat/full-width/
  labelled with the red indicator on the current tab.

## Job 3 — Feed search = a pushed standalone Search page

**SETTLED BEHAVIOUR (his final word, 2026-10-30 09:11 —
record it; do not re-open the flip-flop):** tapping the Feed
header's 🔍 opens the smart Search UI as a full-screen page
PUSHED over the Feed. Not a bottom-nav tab switch (8.90 —
rejected), not the 8.92 in-feed expanding row (rejected,
removed here). The Feed stays the selected tab underneath
and Back returns to it exactly where the user left it.

Implementation (reuse, no duplication of the 8.87 smart
Search):

- `mobile_navigation.xml`: new destination
  `navigation_feed_search` hosting `SearchFragment`, plus
  action `action_navigation_feed_to_navigation_feed_search`
  on `navigation_feed`. The destination declares the same
  `search_query` argument as the tab destination, plus
  `standalone_search` (boolean, default true). It is
  deliberately NOT added to MainActivity's nav-visible
  destination list, so the bottom bar hides while the page
  is open — the same treatment as `navigation_feed_watch` —
  and the bar's selection therefore never leaves Feed.
- `FeedFragment.setupTopBar`: the 🔍 click now calls
  `activity?.navigate(R.id.action_…_feed_search)`. Feed
  scroll state survives the push via the fragment's existing
  `listState` save/restore (onDestroyView / onBindingCreated)
  — the same mechanism the watch page relies on.
- Removed: the `feed_search_row` from `fragment_feed.xml`
  (row, input, ✕), the toggle/TextWatcher/editor wiring, the
  `pendingSearchText` debounce field, the keyboard helpers,
  and the now-dead `refreshHeaderMetrics`. `closeFeedSearch`
  became `clearFeedQuery()` (query-state reset only) for its
  two remaining callers — the empty-state reset and
  pull-to-refresh. `searchQuery` itself stays: the filter
  machinery (`applySearch`, the chrome scheduler's searching
  branch) still keys off it; no UI writes it any more. The
  Filters-sheet filtering of the grid is untouched.
- `fragment_search.xml` + `SearchFragment`: a back-arrow
  `ImageView` (`@+id/search_back_button`, `ic_baseline_arrow_
  back_24`, GONE by default) at the start of the top bar.
  Only the standalone instance shows it (wired to
  `findNavController().popBackStack()`); the tab instance is
  pixel-identical to before.
- Shared-state isolation (the one real hazard): `SearchFragment`
  uses an **activity-scoped** `SearchViewModel` (upstream
  design), shared with the tab instance, so a leftover tab
  search would otherwise render its results in the pushed
  page under an empty search box. When `standalone_search`
  is set and no explicit query was passed, the instance runs
  the same reset an emptied query performs in the tab —
  `clearSearch()` + `updateHistory()` + `clearSuggestions()` —
  and hides the result containers up front (the visibilities
  `onQueryTextChange` applies for an empty query), so the
  first paint is the plain landing: Trending searches chips +
  All/Movies/Series/Anime tabs from `setupSmartLanding`.
  Everything else is per-instance (adapters, SearchView,
  landing views are fragment fields; the two instances are
  never resumed simultaneously — the tab instance's view is
  destroyed while the pushed page is on top), so the tab
  cannot be corrupted; its next open simply also starts from
  the landing, which is its own cleared-query state. An
  explicit `SEARCH_QUERY` still wins over the reset and runs
  as usual, so the argument path the 8.93 filmography taps
  rely on (they target the tab destination) is unaffected,
  and this destination would honour a query the same way.
- Phone only in practice: TV never navigates to the new
  destination, and the shared layout's back button stays
  GONE there (TV uses its own SearchFragment landing and
  never sets the argument).
